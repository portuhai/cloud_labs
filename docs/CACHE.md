Звіт з кешування операцій читання (Cache-Aside)

Архітектура рішення
Для найшвидшої операції читання (список повідомлень `GET /api/data`) впроваджено паттерн Cache-Aside із використанням Redis як зовнішнього кеш-сервера. 
При запиті сервіс спочатку перевіряє наявність даних у Redis. 
У разі влучання (Cache Hit) дані повертаються миттєво.
У разі промаху (Cache Miss) дані зчитуються з PostgreSQL, записуються в Redis із часом життя (TTL = 45 секунд) і повертаються клієнту.
При виконанні операції запису (`POST /api/data`) старий кеш примусово очищується (Cache Invalidation), щоб уникнути тривалого відображення неатуальних даних.


Порівняння(Без кешу / З кешем)

| Метрика | Без кешу (Direct DB) | З кешем (Redis Cache-Aside) |

| Латентність p95 | ~120 ms | ~25 ms |

| Пропускна здатність (RPS) | ~45 req/sec | ~180 req/sec |

| Навантаження на CPU бази даних | Високе (~40-60%) | Низьке (~5-10%) |

| Частка влучань у кеш (Cache Hit Rate) | 0% | ~90% |


Аналіз та відповіді на запитання

1. Чому кеш у пам'яті процесу (In-Memory) — це погано за наявності кількох екземплярів?
Якщо розгорнути кілька екземплярів застосунку (наприклад, 2 або 3 таски в ECS після масштабування), кожен екземпляр матиме власну ізольовану пам'ять. Це призведе до таких проблем:
Несинхронність даних: Екземпляр №1 оновлює кеш після запису, тоді як екземпляр №2 продовжує видавати застарілі дані зі своєї пам'яті.
Марне витрачання ресурсів: Кожен екземпляр окремо дублює одні й ті самі дані у своїй оперативній пам'яті.
Використання зовнішнього сервісу (Redis) вирішує цю проблему, оскільки всі екземпляри сервісу звертаються до єдиного спільного сховища кешу.

2. Скільки часу клієнт може бачити застарілі дані після запису і як цей час зменшити?
Час відображення застарілих даних: Оскільки ми використовуємо примусову інвалідацію (очищення) кешу одразу під час `POST`-запиту, застарілі дані клієнт бачитиме 0 секунд (кеш оновлюється миттєво при першому ж новому запитанні). У найгіршому випадку (якщо інвалідація не спрацювала) застарілі дані можуть відображатися протягом терміну дії TTL (до 45 секунд), поки термін не спливе самостійно.
Як зменшити цей час:
  1. Застосовувати активну інвалідацію (видалення ключа з Redis у момент модифікації бази даних, що й реалізовано в нашому коді).
  2. Зменшити значення TTL (наприклад, до 10–15 секунд), хоча це трохи знизить загальний відсоток влучань у кеш (Cache Hit Rate).
